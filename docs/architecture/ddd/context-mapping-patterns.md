# 上下文整合模式（Context Mapping Patterns）

選擇符合模型差異、協作能力與維護成本的整合方式。

先判斷是否需要整合，再辨認契約的影響方向與團隊能否共同協商。一條關係可以同時使用開放主機服務、發布語言與下游防腐層。

| 模式或方向 | 中文名稱 | 適用判斷 |
|---|---|---|
| Partnership | 夥伴關係 | 交付成果相互依存，雙方共同排程與驗收。 |
| Shared Kernel | 共享核心 | 共同擁有一小部分模型，雙方協調變更並共同測試。 |
| Customer/Supplier | 客戶／供應商 | 上游在排程及契約決策中納入下游的需求。 |
| Conformist | 順從者 | 下游接受上游模型，減少自行轉譯的成本。 |
| Anti-Corruption Layer | 防腐層 | 下游轉譯上游概念，以保護自己的用語與規則。 |
| Open Host Service | 開放主機服務 | 上游為多個使用方提供穩定的整合介面。 |
| Published Language | 發布語言 | 透過明文定義的交換格式與語意達成互通。 |
| Separate Ways | 各行其道 | 整合成本高於收益時，各自解決所需問題。 |
| Upstream / Downstream | 上游／下游 | 標示模型或契約的影響方向，可與前述模式一起使用。 |

最後一項描述關係方向；僅知道誰是上游，仍不足以判定雙方採用客戶／供應商或順從者模式。

**設計產出**　記錄選擇理由、雙方責任與驗證方式。宣稱共享核心時，應能指出共同維護哪一小塊模型。
