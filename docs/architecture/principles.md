# 開發原則與決策

> 預設：模組化單體＋輕量 Hexagonal＋Go 慣例。
> 先依本頁選做法，再到整合文件查技術細節。

## 1. 原則如何落地

| 方法 | 採用程度 | 實際做法 |
| --- | --- | --- |
| Go Idioms | 必要 | 小介面、組合、明確錯誤處理、傳遞 `context` 並限制外部呼叫時間 |
| KISS／YAGNI | 必要 | 先維持一個服務；有當前需求與證據後再增加功能或抽象 |
| 模組化單體 | 預設架構 | 按業務能力拆模組，統一部署 Cloud Run |
| 輕量 Hexagonal | 外部依賴邊界採用 | 隔離 HTTP、LINE SDK 與 Firestore，業務不依賴 SDK 型別 |
| DDD | 選擇性採用 | 先統一業務用語與邊界；規則複雜後才引入完整領域模型 |
| 明確依賴注入 | 預設做法 | 建構函式接收依賴，在 `main` 組裝，通常不需要 DI 框架 |
| DRY | 依知識判斷 | 共用同一業務規則；外觀相似但變更原因不同的程式可分開保留 |
| 測試與可觀測性 | 必要 | 業務單元測試、HTTP 測試、Firestore emulator、`slog` |

## 2. 遇到問題直接選

| 當你要做… | 優先做法 |
| --- | --- |
| Webhook 與 MINI App 提供相同操作 | 兩個入口呼叫同一使用案例 |
| 新增 Firestore 讀寫或 LINE 發送 | 在業務使用端定義所需的小介面，由 adapter 實作 |
| 新增只有一處使用的簡單判斷 | 先寫清楚的函式，等責任與需求出現再抽象 |
| 新增業務規則 | 在業務層實作，先驗證成功與拒絕案例 |
| 同時更新多筆相關資料 | 評估 Firestore transaction，外部副作用放在 callback 外 |
| 保證資料更新後最終送出通知 | 定義失敗語義；有可靠投遞需求時再設計持久化工作／outbox |
| 改善效能 | 先量測，再用 benchmark／pprof 驗證 |
| 引入新架構或框架 | 說明目前問題、簡單方案的限制與驗證方式，再記錄 ADR |

## 3. 每次功能交付順序

1. 定義入口、可信身分、輸入與預期結果。
2. 在使用案例實作業務規則與授權。
3. 接上必要 adapter，明確處理逾時與失敗。
4. 驗證成功、拒絕、重複請求與下游失敗。
5. 確認日誌可追查且不含 token、機密或不必要的個資。

## 4. 邊界檢查

- Webhook：先驗證原始 body 的簽章，處理重送冪等性，詳見 [LINE](../integrations/line.md)。
- MINI App：後端驗證 LINE 身分，再檢查資源存取權；不信任前端 user ID。
- Firestore：server SDK 的授權由後端與 IAM 負責；交易 callback 可能重跑，詳見 [Firestore](../integrations/firestore.md)。
- 並行工作：明確管理取消與生命週期；需要可靠完成的工作使用持久化機制。

目前先不引入微服務、完整 CQRS、Event Sourcing 或通用 Repository 框架。
當獨立部署、讀寫差異或事件稽核需求成立時，再重新評估。

實作細節見 [Go 慣例](../development/go.md)；驗證方式見 [測試](../development/testing.md)。
