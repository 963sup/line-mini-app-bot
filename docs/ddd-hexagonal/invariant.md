# 不變條件（Invariant）

Invariant 是模型在約定的一致性邊界內、每次成功操作後都必須維持的規則。應區分物件始終有效的條件、操作的前置條件，以及允許延後完成的跨邊界流程。

## 規則放在哪裡

| 規則                           | 責任位置                                     |
| ------------------------------ | -------------------------------------------- |
| 時間區間起點不得晚於終點       | Value Object 的建立與運算                    |
| 已撤銷邀請不得再接受           | Invitation 的合法狀態轉換                    |
| 移除後仍至少保留一位 Owner     | 決定該規則的 Aggregate 及一致性策略          |
| 只有目前有管理資格者能移除成員 | 用例協調授權與領域政策，並依風險納入交易     |
| 通知最終送達                   | 可靠投遞流程的承諾，不是假設資料提交就已成立 |

前端輸入限制可改善互動，但不能替代後端模型與交易保護。

## 前置條件與併發

邀請尚未到期是接受操作在指定服務端時間的前置條件；時間過去不表示整個既存邀請物件變成無法存在。需要最新外部事實的條件，須記錄來源、版本與有效時間。

兩個請求可能各自檢查成功、合併後違規。必須定義交易讀集合、版本或其他衝突機制，不能只加一個布林驗證函數。

## 將規則轉成可驗證條件

1. 用領域語言寫出規則及反例，例如「完成量不得超過總量」，避免只寫「資料必須正確」。
2. 定義適用範圍與成立時點：建立、每次異動後、提交時，或允許延遲的流程終點。
3. 列出判定所需事實、可信來源、版本與時間，指出由哪個模型或政策擁有此規則。
4. 寫成可判定條件，再列成功、邊界與拒絕例子。缺值與零值、未知與失效不可混用。
5. 找出兩個各自合法卻合併違規的操作，據此決定[聚合](aggregate.md)及[儲存交易](transaction.md)的保護範圍。

## 規則紀錄範本

| 欄位           | 要交付的內容                               |
| -------------- | ------------------------------------------ |
| 規則 ID 與來源 | 所屬領域規格、決策者、已確認或待決策       |
| 命題與作用域   | 對哪個資源、在什麼條件下必須成立           |
| 成立時間       | 操作前、提交後，或有明確期限的後續完成     |
| 事實與擁有者   | 判定函數、時間、權限／狀態來源及讀取版本   |
| 拒絕語意       | 可辨識錯誤、原資料保留及允許的後續操作     |
| 一致性證據     | 交易讀寫集合、版本條件、併發反例及測試位置 |

規則 ID 是追蹤方式，無須為此建立通用規則引擎。相同規則由一處維護，其他入口經相同模型或用例執行。

## 範例與測試分工

假設一項工作以已知總量追蹤進度，規則為 `total > 0` 且 `0 <= done <= total`。完成量為零、介於零與總量之間、等於總量時，可分別推導未開始、進行中與完成。缺值須另行定義，不能直接視為零。

| 案例                    | 要驗證的結果                         |
| ----------------------- | ------------------------------------ |
| 總量 5，完成量 0／3／5  | 各自得到合法狀態                     |
| 總量 5，完成量 8 或負數 | 拒絕，不寫入新進度                   |
| 等值十進位表示          | 不因字串表示不同產生不同數量判定     |
| 兩次更新使用同一舊版本  | 依版本契約衝突，不讓舊資料覆寫新結果 |

前三類由模型測試驗證；最後一類需核對保存交易。純函數通過不能證明競爭寫入安全。

## 設計產出與核對

每條規則列出適用時間點、擁有者、所需事實、拒絕結果與一致性方式。用成功、非法轉換及併發反例檢查規則，實際驗收依既有階段政策。
