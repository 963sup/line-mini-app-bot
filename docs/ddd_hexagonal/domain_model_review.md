# 領域模型審查

以可推翻模型的案例檢查設計品質，適用於新能力、規則變更、聚合拆分及契約演進。局部修正只審受影響項目；本頁是設計驗收方法，不代替功能規格或實際測試。

## 檢核清單

| 面向       | 審查問題                                     | 必須出示的證據                                                |
| ---------- | -------------------------------------------- | ------------------------------------------------------------- |
| 語言       | 同一名詞是否有不同詞義？誰有權解釋？         | 成功／拒絕例句、詞彙與上下文擁有者                            |
| 規則       | 每條規則由誰維護、何時成立？                 | [不變條件](invariant.md)與規則到判定位置的對照                |
| 身分與值   | Entity、Value Object 的選擇能否說明？        | 身分延續、相等與非法值案例                                    |
| 聚合       | 邊界是否來自一致性需求，而非畫面或父子關係？ | [聚合設計](aggregate.md)、最大規模與競爭寫入結果              |
| 授權       | Actor 的身分及資源歸屬是否可信？             | [授權矩陣](domain_authorization.md)、外部事實時效與交易重查點 |
| 生命週期   | 非法轉換、終態及重送如何處理？               | [轉換表](state_machine.md)、拒絕後原狀態                      |
| 公開契約   | 消費者能否區分拒絕、衝突與不可用？           | [契約](domain_contract.md)、錯誤映射與版本相容組合            |
| 保存與恢復 | 部分失敗會否留下不一致？                     | 讀寫集合、提交點、重試與修復責任                              |
| 可驗證性   | 測試能否辨識錯誤模型？                       | 具體反例、測試位置、實際結果與限制                            |

## 必須嘗試的反例

- 兩個請求都讀到相同版本，各自合法但合併後違規。
- 檢查資格後資源停用或歸屬改變；外部資格查詢失敗。
- 寫入已提交但回應遺失，同一操作重送或換內容重送。
- 舊客戶端遇到新增狀態、缺欄位資料或已失效的跨庫引用。
- 拒絕時發現部分寫入、先發通知後提交失敗，或模型偷偷依賴資料庫／HTTP。

每個反例寫出「初始事實 → 操作／交錯順序 → 允許結果 → 禁止結果」。只寫「需支援併發」不能作為驗收標準。

## 規則擁有者與結論

業務規則由所屬領域的決策者確認；用例負責協調，Adapter 與交易實作負責保存保證。跨上下文爭議記錄提供方、消費方與決策責任，不由共用套件自行決定。

審查結論逐項標記「有證據通過」「需修正」「待決策」或「不適用及理由」。交付規則／用例／契約／程式／測試對照、未解問題、決策者與驗收方式。有關正確性的未決事項不得被總體通過掩蓋；測試尚未執行就保留未驗證狀態。

## 實際驗收

模型單元測試驗證判定；儲存整合測試驗證交易與競爭；契約測試驗證對外語意；架構檢查驗證依賴方向。單次成功、圖譜或打包內容無法替代上述行為證據。
