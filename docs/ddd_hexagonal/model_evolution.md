# 契約與模型演進

既有 HTTP 消費端、儲存文件或待處理事件可能跨越兩次部署。模型改名、欄位拆分或調整語意前，先列出哪些版本仍會同時讀寫，以及誰有權解釋舊值。公開 DTO、持久化格式與領域物件各自有演進時程。[防腐層](anti_corruption_layer.md) · [整合事件](integration_event.md)

## 示例：將單一狀態拆成兩個事實

假設舊欄位「完成」要拆成「決定已記錄」與「結果已套用」。一個舊布林值可能不足以推導兩者。先查歷史資料能否還原；無法還原時，保留未知狀態並交給規則擁有者決定呈現方式。直接把兩欄都填 true 會製造從未觀察到的業務事實。

1. **擴充。** 先讓讀端接受舊格式與新格式，在 Adapter 邊界轉譯，確認舊客戶端如何處理新增欄位或枚舉。未驗證前不假設所有新增欄位都相容。
2. **遷移。** 明訂唯一權威寫入來源。若有回填，依版本條件更新，使再次執行能略過已處理資料，也能避免覆寫較新的業務變更。記錄未知、衝突與失敗筆數。
3. **切換與收縮。** 比對新舊讀取結果，確認仍在線的消費端、舊事件與回放期限，再移除舊格式。若新資料已無法由舊版解讀，回退應走相容讀端或前向修復；單純回部署舊映像可能使資料不可讀。

## 契約責任

公開語意、錯誤與版本承諾先依[上下文公開契約](domain_contract.md)記錄。不同版本的格式可讀，不代表語意仍相容。

## 驗收

至少檢查「新讀端讀舊資料」「舊讀端遇到新資料」「回填與使用者寫入競爭」「失敗後再次執行」。無法支援的組合要有部署順序或版本隔離。契約變更時核對消費端如何理解新舊資料。型別或產生碼一致仍需驗證歷史資料的語意。
