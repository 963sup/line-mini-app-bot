# Markdown 文件規範

本文件是本儲存庫自有 Markdown 的編寫、審查與修正規範唯一權威來源。目標是以最低必要文字與結構，傳達準確、完整、無歧義、可執行、可驗證且可維護的意圖，降低理解成本與 token 使用；不得為縮短篇幅犧牲正確性或必要資訊。

## 適用範圍與要求等級

所有角色新增、修改或審查自有 Markdown 時 MUST 遵守本規範，包括 README、AGENTS 與專題文件。MUST 表示必要要求，MUST NOT 表示禁止，SHOULD 表示有具體理由才可偏離的建議，MAY 表示可選做法。偏離 SHOULD 時 MUST 說明理由及影響。

完整自有文件適用下列結構要求；嵌入其他文件的 Markdown 片段 MAY 依宿主層級省略 H1。生成文件、vendor 與上游安裝技能 MUST 保留其來源格式，不得為套用本規範直接改寫；必要修正 MUST 回到其來源或產生流程，另取得對應檔案所有權。例外 MUST 有可辨識的來源或用途，不得將一般 README 視為片段而跳過要求。

## 編寫原則

### 1. 清楚性（Clarity）

文字 MUST 直接、精確；每段 SHOULD 聚焦一個主要概念。MUST 明確區分規則、事實、假設、建議與範例，定義讀者無法由上下文確定的術語，避免模糊指代及多種解讀。

### 2. 精簡性（Conciseness）

MUST 刪除冗詞、重複敘述及無關背景，SHOULD 使用簡短但完整的句子。MUST 保留理解、決策、執行與驗證所需的資訊；不得只以字數或 token 減少判斷改善。

### 3. 結構（Structure）

MUST 使用標準 Markdown；每份完整自有文件 MUST 有且只有一個明確的 H1，後續標題依 H2、H3 逐級展開，不得跳級。標題 MUST 描述內容，不得以「其他」「補充」等無法導航的名稱代替具體主題。SHOULD 用表格比較平行項目、清單列規則或步驟、程式碼區塊呈現指令與程式範例；不得為排版增加無助理解的結構。

### 4. 單一事實來源（Single Source of Truth）

每條規則 MUST 只有一個權威維護位置，其他文件以相對連結引用，不得複製完整政策。更新或合併規則時 MUST 檢查所有相關引用、索引與錨點，確保讀者可找到有效來源且敘述一致。

### 5. 可執行性（Actionability）

指令與規則 MUST 使用明確動詞，交代適用條件、限制及預期結果，並依要求等級使用 MUST、MUST NOT、SHOULD、MAY。MUST 避免以「盡量」「適當」「最好」等無法判定完成條件的措辭代替具體要求。

### 6. 上下文效率（Context Efficiency）

MUST 將重要結論、限制與必要操作放在前段，將背景、範例與參考資料分離。SHOULD 讓讀者或代理按需載入詳細內容，不得將所有主題集中為必須一次讀完的巨型文件。

### 7. 一致性（Consistency）

相同概念 MUST 使用一致術語與名稱，標題和格式 SHOULD 保持一致。路徑、指令、參數與程式碼 MUST 對照有效來源，避免錯誤或互相矛盾的敘述；不得憑記憶補齊未確認的技術細節。

### 8. 可驗證性（Verifiability）

技術事實 MUST 可追溯至實作、規格或適用版本的權威來源，明確區分已驗證結果與假設。操作 MUST 有明確完成條件；檢查報告 MUST 記錄實際執行及限制，MUST NOT 將未執行、工具可用或配置存在說成測試通過或功能已驗收。

### 9. 可維護性（Maintainability）

SHOULD 依主題與責任拆分文件，移除已確認過時、重複或不適用的內容，同時保留仍有效的知識與重要限制。MUST NOT 建立尚無實際內容或維護責任的文件與分類；結構調整 MUST 改善後續維護，而非只做一次性美化。

### 10. 漸進揭露（Progressive Disclosure）

入口文件 MUST 提供核心規則與導航，專題文件保存詳細內容，範例與參考按需讀取。MUST NOT 要求每次任務讀取全部文件；代理 SHOULD 先讀適用入口，再依任務範圍讀取所需專題。

## 編寫與修正流程

1. **Identify**：確認文件目的、讀者、範圍、權威來源及本次檔案所有權。
2. **Analyze**：辨識重複、歧義、矛盾、過時內容及缺少證據的敘述。
3. **Consolidate**：合併重複至權威位置，統一術語，更新必要引用。
4. **Simplify**：移除不必要文字與結構，不犧牲完整意圖。
5. **Organize**：依重要性與操作順序安排內容，分離背景、範例與參考。
6. **Validate**：核對語意、相對連結與錨點、指令、來源及完整性，記錄實際檢查結果。
7. **Preserve**：對照原文與來源，確認仍有效的知識、必要資訊與重要限制均被保留。

## 自主修正與所有權

代理 MUST 在任務擁有的 Markdown 檔案或 hunks 內，自主修正有證據的不合規內容，包括格式、冗詞、語意相同的重複及失效引用；修正 MUST 保留原意與必要資訊。必要的直接引用更新 MUST 納入明確所有權，每份檔案同時只能有一個寫入者。需要額外檔案時 MUST 先由協調者調整分派，保留使用者與其他工作的既有變更。

遇到歧義、來源衝突或無證據的技術內容，MUST 依根指引查證；證據不足時 MUST 回報具體待確認事項，MUST NOT 臆造產品規則、技術事實或需求決策。程式碼、工具或設定的必要變更 MUST 交回協調者安排。全庫掃描或重寫 MUST 有明確任務授權，不得因發現一處問題自行擴展範圍。

## 驗證與完成條件

交付前 MUST 審查本次 diff，執行 `git diff --check`，核對變更文件的本機連結、標題錨點、來源路徑及相關引用。涉及設定時 MUST 執行既有的 `bash scripts/tooling/tool-exec.sh python3 scripts/tooling/check-config.py`。該檢查不涵蓋所有 Markdown 結構、錨點或語義；MUST 另做適用的人工或工具核對，不得宣稱不存在的文件檢查任務已執行。

適用指令 MUST 核對語法、參數與前置條件；需要憑證、外部寫入或部署的指令不得只為驗證文件而執行。未實際執行時 MUST 說明來源核對與執行驗證的差別。完成報告 MUST 列出修正範圍、來源、實際檢查及剩餘不確定性；格式檢查成功不能取代正確性與語義審查。

## 決策優先序

- 清楚性優於極端精簡。
- 正確性優於 token 減少。
- 單一事實來源優於重複敘述。
- 可執行指引優於抽象口號。
- 必要上下文優於孤立的短指令。
- 簡單結構優於過度分類。
- 可維護性優於一次性美化。

最終目標：**Write for accurate machine interpretation and efficient human maintenance.** 以最少必要資訊傳達完整、可驗證的意圖，不增加無助理解、決策或執行的內容。
