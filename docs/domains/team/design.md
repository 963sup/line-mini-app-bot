# 團隊管理與指派

## Team（團隊）

| 資料或操作 | 規則與驗收條件 |
|---|---|
| `teams/{teamId}` | 文件 ID 等於 LINE groupId。首次綁定時成對寫入 managementScope（organization 或 enterprise）及 managementId（對應層級的 ID）。每個 Team 只有一個管理歸屬，舊群組可暫未綁定。 |
| 綁定群組 | 指定管理歸屬須具目標管理範圍的管理權及該群組的管理授權。交易內確認原歸屬；同一綁定可重送，不同管理者競爭時只有一方成功。可信 LINE 群組事件沿用既有流程自動建立 Team，不需人工核准；管理歸屬另行設定。 |
| `organizations/{organizationId}/enterpriseTeams/{teamId}` | 記錄一個 Enterprise Team 在此組織的指派。同一 Team 可指派給同企業的多個組織；成員名單由企業集中維護。 |

例如總部「資安組」可以用同一個 teamId 指派至台灣與日本兩個組織，各組織分別授予 Repository 權限。「台灣排班組」由台灣組織管理，只在台灣使用。後端判定資源存取時須核對目前的組織歸屬或有效指派、使用者資格及個別資源授權；既有 LINE 資料仍遵循原功能的成員核驗規則。

既有出勤與摘要繼續以原 groupId 查詢。既有群組在明確綁定前維持未歸屬；組織所有權本身不授予 LINE 群組資料讀取權。


## 獨立 Membership 的讀取邊界

團隊文件的 `membershipMode` 選定授權來源。空值及 `legacy` 沿用既有 LINE 群組資格；`membership` 只採獨立成員關係。未知模式、停用團隊或不存在的資格均不放行。Team 擁有管理歸屬與團隊狀態；Membership 擁有成員關係及上層資格判定。Bootstrap 將查詢能力接到組織與企業團隊列表，與各自的候選團隊讀取共用 Firestore 交易。

獨立模式須同時存在 Team 的有效 `member` 或 `maintainer` 關係、由管理歸屬指定的有效上層關係，且上層 generation 要與 Team 關係保存的版本一致。Enterprise Team 指派只是組織的候選來源；在組織列表中仍須先具備該組織可見資格。LINE 群組資料與原有群組操作繼續適用自身的資格規則。

Team 管理歸屬操作拒絕沿用獨立模式團隊的舊管理者欄位。維護成員資格與變更團隊管理歸屬是兩項不同能力。


## 授予、撤銷與首次開通

| 操作 | 規則 |
| --- | --- |
| 授予 `member` | 管理範圍的授權管理者，或具有效上層資格的 Team `maintainer`，可以授予。受授者必須已有同一管理範圍的有效資格。同一交易保存 Team 角色及上層世代。 |
| 授予或撤銷 `maintainer` | 只由管理範圍的授權管理者操作。Organization 採有效成員關係加上匹配的 Owner 指標；Enterprise 採有效 `owner` 或 `manager` 關係。Team maintainer 不得透過授予或撤銷普通成員來改寫 maintainer 關係。 |
| 撤銷 `member` | 管理範圍的授權管理者或有效 Team maintainer 可執行。將關係改為 removed 並增加版本。上層撤權時讀取立即失效，無須先刪除 Team 紀錄。 |
| 併發與重送 | 命令帶預期關係版本，首次授予使用 0。有效資格不變時無須增加版本；重新授予已移除或依賴過期的關係增加世代及版本。重送鍵綁定渠道、Team、Actor、命令、目標與輸入；與原異動原子保存。舊版本不得改動新關係。 |
| 首次開通 | 沒有既有 Team 資料要匯入。只有 Bot 已觀察到的啟用 LINE 群組可開通。操作者須同時具備該群組管理授權和目標 Organization／Enterprise 的有效管理資格。操作者明確選定具有效上層資格的第一位 `maintainer`。 |

開通在同一筆交易讀取 Team 狀態、LINE 群組管理授權、上層管理權與接任者資格。成功時一併保存 Team 的管理歸屬和 `membershipMode=membership`、首任關係與上層世代，以及開通稽核。不同管理範圍或不同首任人員的並行開通只能有一方成功。相同開通重送重新驗證發起者管理權後回成功，不重新授權首任人員。Team 保存首任身分作為開通重送的比對事實；當前角色以 Membership 關係為準。

既有 `PUT /api/v1/teams/{teamId}/management` 帶 `initialMaintainerUserId` 時執行獨立開通。原請求格式保留相容用途。頁面仍沿用現有團隊區，群組管理授權由既有來源提供。正式使用前須上層已建立可驗證的獨立資格，且團隊有可驗證的 LINE 群組管理授權。現行觀察流程只投影群組名稱及狀態，尚無為新團隊核發管理授權的正常入口；Bot 加入群組或收到群組訊息不等於取得此授權。後續成員授予、撤銷雖有交易實作，仍待接上具名 HTTP 操作與最小介面。



## 正常入口與開通阻塞條件

以下為未來設計的交付要求，不表示現有頁面或 API 已完成。

| 流程 | 必須形成的操作閉環 |
| --- | --- |
| 取得群組管理授權 | 必須明定誰可核發、憑什麼證據、授權對應的渠道／群組／使用者、有效期及撤銷入口。核發來源尚待產品與可信證據方案定案，MUST NOT 以 Bot 入群、一般群組訊息或自行填入 ID 代替。未定案前禁止開通。 |
| 首次開通 | 管理者在所選 Organization／Enterprise 的團隊區選定可管理群組及可辨識的首任 maintainer，確認管理歸屬後送出。後端依前節同一交易提交，成功後刷新列表；失敗保留未開通狀態並回傳可處理的原因。 |
| 名單與角色管理 | 最小介面提供名單、授予／變更 member 或 maintainer、撤銷與確認結果。可選人員來自有效上層資格，不能要求使用者自行輸入原始 LINE ID。服務端重新核對資格、版本及角色政策；確切 HTTP 路徑、DTO、分頁與錯誤映射須先納入 OpenAPI。 |
| 上層撤權與重新加入 | 上層撤權提交後，Team 資格立即無效。重新加入上層後，管理者須明確重新授予；舊關係不自動恢復。名單與操作能力須反映目前有效性。 |

Organization Team 須先完成 Organization 的獨立資格閉環；Enterprise Team 另須先完成 [Enterprise 直接資格](../enterprise/design.md#獨立資格與治理的交付邊界)。若沒有有效 maintainer，上層授權管理者仍可依既定角色政策重新授予；不得回退舊群組管理欄位。首次開通範圍不提供改掛另一管理方，後續歸屬移轉須另訂依賴失效與重新授權契約。

驗收至少覆蓋無群組管理授權不能開通、雙方競爭開通僅一方成功、重送不重新授權、maintainer 不能改寫 maintainer、撤權與授予競爭遵守版本、上層退出再加入不恢復舊 Team 權限。正常入口、可信授權來源與資料庫併發證據齊備後，才可標示首次開通閉環完成。
