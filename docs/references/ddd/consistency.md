# 一致性與交易（Consistency）

一致性設計要回答：哪些規則何時必須成立、其他人能何時看見結果，以及失敗或重送後留下什麼。Aggregate 是業務邊界，資料庫交易是實現一致性的技術手段，兩者不能直接畫等號。

## 選擇一致性方式

| 情境 | 必須說明的設計 |
| --- | --- |
| 同 Aggregate 的原子異動 | 所需讀取、根的版本、完整寫入與衝突處理 |
| 跨 Aggregate 可延後完成 | 已完成部分、尚待完成部分、重試及補償狀態 |
| 跨 Aggregate 必須立即一起成立 | 先重新評估邊界；若採本機共用交易，記錄耦合、成本與限制 |
| 跨外部系統 | 不假設本機交易能涵蓋遠端；定義可重試、結果未知與補償 |

這些是設計選項，不授權導入分散式交易、Saga 或新事件平台。

## 防止檢查與寫入之間失效

授權或規則依賴的狀態若會同時改變，必須將對應版本與資料寫入放進能檢查衝突的一致性機制。取得 actor 的 Session 不代表角色永遠有效；獨立查資格後無條件寫入，無法保護併發撤權。

兩位 Owner 同時退出是未來設計的反例：各自讀到還有另一位 Owner，不能因此都成功。必須共享可競爭的狀態或以等效機制防止違規，不只是各鎖住自己的成員文件。

## Unit of Work 與重試

Unit of Work 定義一次提交中可以使用的 Repository／Reader 能力及生命週期。核心契約可將 SDK 交易物件留在 Adapter 內；Adapter 將這些能力綁定至同一技術交易。共用資料庫 client 或沿用同一 request context 不代表共用交易。

callback 若可能重跑，內部不得發送 外部訊息或進行不可撤回副作用。識別碼、服務端時間及請求指紋如何固定，須依用例明定；失敗嘗試不能洩漏為成功結果。

## 冪等與結果未知

定義防重鍵的 Actor／資源／操作範圍、內容指紋、保存期限與可回放結果。同鍵不同內容應衝突；過期版本不得靜默覆蓋。逾時可能發生在提交之後，不能把 unavailable 一律解釋成「沒有寫入」。

資料提交與外部投遞分開回報；提交後通知失敗，不應重新執行已成功的業務異動。是否需要可靠投遞依具體用例決定。

## 設計產出與核對

記錄原子邊界、讀寫集合、版本、撤權生效時間、可觀察中間狀態、重送與取消語意。驗收條件可列併發及故障情境。
