# 領域授權與業務規則

本頁是設計指引。授權回答「誰可以對這個資源執行此操作」，領域規則回答「目前狀態允許產生什麼結果」。兩者都必須成立。

## 決策所需事實

| 要素 | 要確認的內容 | 常見反例 |
|---|---|---|
| Actor | 由身分入口驗證的操作者，包含必要的服務身分 | 接受請求內自行指定的管理員角色 |
| Resource | 從保存資料取得的擁有者、Repository 與作用域 | 只比對 URL 的資源 ID，未核對實際歸屬 |
| Action | 具名業務操作，例如編輯內容、分類、核准 | 將「可讀取」當成「可修改」 |
| Policy | 規則擁有者、判定所需事實及拒絕原因 | 讓 UI 是否顯示按鈕決定後端資格 |
| State | 目前版本、狀態及判定時間 | 沿用列表快取的啟用狀態完成寫入 |

Authority 表示權限來源與有效範圍；Policy 可描述授權條件或業務政策，但文件及測試須分開這兩種拒絕。系統成功執行「駁回申請」不等於系統拒絕操作。

## 責任與執行位置

1. 入站 Adapter 驗證身分、解析輸入，不採信客戶端的擁有權聲明。
2. 用例取得資源與外部資格事實，保留取得失敗、查無資格及資料過期的差異。
3. 領域方法或政策依明確輸入判定，不自行存取 HTTP、Session 或資料庫。
4. 儲存 Adapter 在交易中重新取得必須與寫入一致的資源、版本及資格事實，再執行判定與保存。
5. 入站 Adapter 依公開契約映射拒絕、衝突及不可用；避免透過錯誤差異洩漏未授權資源是否存在。

外部服務的成員資格查詢與本地資料庫提交不構成跨服務原子快照。若資格在呼叫後改變，須明定允許的觀察時間與風險，不能宣稱「放進交易」就能解決外部事實的競爭。

## 示例

審核政策可要求審核者屬於申請範圍且不是申請人。內容編輯與分類也可有不同授權條件，並各自檢查寫入版本。

## 設計產出與驗收

每個 Action 交付允許／拒絕矩陣、事實提供方、資料新鮮度、交易重查點與錯誤映射。至少涵蓋本人／他人、同庫／跨庫、停用資源、資格服務不可用、過期版本及檢查後資格改變。拒絕後不得留下部分業務寫入；交易競爭須以儲存整合測試驗證。
