# 事件溯源（Event Sourcing）

**採用方式：按需。** 本頁為進階設計參考，不是目前架構的必要條件，也不表示專案已實作此模式。採用前須以具體用例、替代方案及成本評估決定，必要時依既有 ADR 流程記錄。

Event Sourcing 使用持久事件序列作為狀態權威來源，透過依序套用事件重建模型。目前狀態表、Audit 或已發送的 Domain Event，不能單憑存在就稱為 Event Sourcing。

## 何時按需採用

業務確實需要依歷史事實重建狀態，且事件生命週期本身有價值時再評估。只有查異動紀錄的需求，可能用目前狀態加 Audit 即可。

採用前須評估事件契約長期維護、重播、遷移、資料保留與除錯成本；不是對整個系統統一替換儲存方式。

## 寫入與重建

命令依目前重建狀態驗證，產生新事件，並以預期 stream version 追加，防止並行寫入遺失更新。重試仍須防重；重新讀取後也必須重新判斷命令是否有效。

重播採用既有事件重建結果，不重新執行原命令的授權，也不能再次寄信、扣款或發出外部通知。依賴現在時間或外部回應的決策，須將重建需要的事實記錄下來。

Snapshot 是加速重建的衍生資料，不取代權威事件流；需標明對應版本及失效策略。讀取投影可以重建，但同步延遲與存取授權仍須單獨設計。

## 事件演進與限制

舊事件須可由新版程式解讀；變更時採明確版本與轉換策略，不隨意改寫歷史。追加更正事件也不會自動刪除舊個資，須先設計資料最小化、保留與刪除要求。

Event Sourcing 不要求微服務或 CQRS；CQRS 也不要求 Event Sourcing。使用資料庫事件記錄來通知另一系統，與以事件重建領域狀態是兩個決定。

## 設計例子與核對

若未來確定要用成員關係事件重建任一時點資格，須完整定義角色、移除、重新加入與上層資格的歷史語意。不能直接將 Audit 當成事件流而宣稱已可重建。

列出 stream 身分、順序、併發控制、契約演進、快照、投影、重建耗時、資料生命週期與遷入／遷出方案。驗證重播不會產生外部副作用。
