# EventStorming 領域探索

EventStorming 是跨角色共同探索業務的工作坊方法。適合詞義有爭議、流程跨團隊、例外多或邊界未明的問題。它產生可核對的流程與問題，不直接決定資料表、微服務或事件平台；本頁為探索方法。

## 參與者與範圍

邀請實際操作者、規則決策者、開發與維運代表，先選一個可講述的業務場景，記錄起點、完成標準與範圍外事項。缺少規則擁有者的結論標記待確認，不用技術投票取代產品決策。

## 從事件找到規則

1. 將已發生的業務事實按時間排列，例如「補正已提出」「審核決定已記錄」。資料寫入或 HTTP 呼叫不是必然有業務意義的事件。
2. 回溯每個事件的命令與 Actor，例如誰提出「核准補正」，命令被拒絕時不應產生成功事件。
3. 標出決策需要的查詢資訊、外部系統及政策，例如收到某事實後何時提出下一個命令。政策不是永遠會成功的自動流程。
4. 加入重送、取消、逾時、並行與部分失敗；將詞義衝突、未知順序或未決規則標為熱點，指定負責人及查證方式。
5. 找出語言改變、事實擁有者與交易要求不同的區段，提出候選上下文及聚合，回到實例驗證邊界。

## 工作坊紀錄

| 元素 | 記錄內容 | 不應直接推定 |
|---|---|---|
| 命令 | 操作者的意圖、資源、前置條件 | 一定成功或一定要新增 API |
| 事件 | 業務已承認的事實、發生時點與擁有者 | 一定發布或永久保存 |
| 政策 | 觸發條件、所需事實、下一步與失敗處理 | 必須使用訊息佇列 |
| 熱點 | 爭議、缺少證據、決策者與下一步 | 已有共識 |
| 候選邊界 | 語言、規則與一致性的分界 | 必須拆成獨立服務 |

## 例子與完成條件

以申請審核為例，詢問「審核已記錄，但申請結果仍未更新，算完成嗎？」角色對完成時間的理解若不同，應先確認事件名稱與可見性承諾，再決定是同一交易還是兩個流程步驟。

交付成功與拒絕時間線、共識詞彙、命令／事件／政策清單、候選邊界、熱點負責人及反例。選一個案例從意圖走到結果，再用競爭與失敗場景推翻假設；可辨識的規則轉入[不變條件](invariant.md)、[狀態機](state-machine.md)與[公開契約](domain-contract.md)。

方法來源：[EventStorming 官方說明](https://www.eventstorming.com/)。採協作探索方法，不預設事件驅動部署。
