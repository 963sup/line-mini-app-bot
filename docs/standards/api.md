# API 規範

## 契約與產物

- MUST 以 `api/contract/` 的 OpenAPI 作為 HTTP 契約的唯一權威來源。
- MUST 依序修改契約、重新產生並驗證受影響的產物、更新後端 adapter，再更新前端消費端。契約、產生碼、adapter、前端與測試須在同一變更同步。
- MUST NOT 在 OpenAPI 之外建立平行的公開 HTTP 契約，或新增未登錄的公開操作。
- MUST NOT 手動修改契約產物，或將傳輸 DTO 作為領域實體或持久化模型。
- SHOULD 使用由契約生成的型別與 client。
- SHOULD NOT 僅因命名便利而複製等價 schema。

## 資源與操作

- 公開 API 使用 `/api/v1` 前綴；內部端點與診斷端點使用獨立契約。
- SHOULD 採用標準 HTTP 語意及資源導向設計，使用穩定的資源識別字。
- 路徑以資源與具名業務操作表達。MUST NOT 暴露資料庫集合、持久化結構或內部套件。
- 操作契約需定義 Actor、Resource、Action、前置狀態、成功結果與可辨識失敗。
- 列表需定義穩定排序、分頁游標、篩選語意及回傳欄位。SHOULD 依實際消費端需求設計分頁、篩選與排序。
- SHOULD NOT 暴露不必要的欄位或操作，或在標準 HTTP 足夠時引入自訂協議。
- SHOULD NOT 在缺乏明確需求時，為個別端點引入不同的傳輸慣例。
- 當有可證明的消費端需求時，MAY 新增 API 投影。

## 輸入與輸出

- MUST 在適用的信任邊界驗證輸入與輸出。HTTP 邊界應明確區分缺少、`null`、空值與零值。
- 時間使用明定格式與時區；業務日期由對應領域時區解釋。
- 共用錯誤格式為 `error.code` 與安全的 `error.message`；客戶端依穩定 code 處理。
- 回應不得洩漏內部錯誤、憑證、個資或資料庫結構。

## 寫入可靠性

可能重送的寫入必須定義 idempotency key 的範圍、相同鍵不同內容的行為、版本衝突及回應遺失後的查詢或重試方式。HTTP timeout 不代表後端未提交。

## 相容性

- SHOULD 優先採向後相容的新增。
- MUST 保持契約相容性。移除或改變既有欄位、狀態碼、enum 或回應語意而造成破壞性變更時，MUST 提供明確遷移方案，先確認所有消費端與遷移窗口。
- SHOULD NOT 只因內部實作改變而新增 API 版本。
