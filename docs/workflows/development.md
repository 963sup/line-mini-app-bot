# 開發流程

## 1. 定位

從使用者入口追到 OpenAPI、用例、Domain、Adapter、資料與測試。先確認目前行為、契約擁有者及工作區既有變更，再決定最小修改範圍。

## 2. 定義結果

對每個操作寫清楚 Actor、Resource、Action、授權、前置狀態、成功結果、拒絕、重送、併發與外部副作用。前端功能同時列出載入、空資料、錯誤與身分切換結果。

## 3. 實作順序

1. 必要時先更新 OpenAPI 或權威設計。
2. 在 Domain／Application 實作規則。
3. 由 Adapter 接上資料庫、LINE 或外部服務。
4. 在 Bootstrap 組裝。
5. 前端使用產生 client 呈現結果。
6. 同步測試與文件。

## 4. 驗證

依[驗證流程](verification.md)選擇檢查。修 bug 時必須重跑原始案例；無法重現或缺少環境時，分開記錄觀察、推論與尚待確認的行為。

## 5. 交付

審閱 diff，確認沒有無關格式化、秘密、失效連結或手改產生檔。回報變更位置、實際檢查、結果及限制；提交與推送依[發布流程](release.md)。

## 交接範本

在目前聊天輸出以下格式，接手者須能判斷版本、範圍與下一個動作。

```text
Goal｜目標與完成條件
Ownership｜儲存庫、分支、提交、相關未提交檔案與負責範圍
Inputs｜必讀檔案、符號、設計或操作限制
Evidence｜已確認的事實、來源、可讀的產物位置與適用範圍
Checks｜已執行的命令、實際結果、未驗證項目
Open issues｜阻礙、待決事項、下一個動作
```

### 重用查核結果

沿用版本、工作樹、範圍及工具設定仍適用的證據；分析報告另核對來源與產物雜湊。只更新失效或缺少的證據；工具失敗時記錄環境與失敗階段，條件未變時不反覆重試。

- HEAD 相同不足以證明證據有效；須核對相關 dirty paths、query／bundle 範圍與來源版本。Context7 只重用相同問題與版本涵蓋的結果；Repomix 另核對包含／排除路徑。

### Repomix 來源範圍

跨檔探索或審查時，用 `--include` 限定來源。先查已有參考包的版本、工作樹變更與檔案清單；涵蓋本次問題即可重用，關鍵片段須與目前來源比對。
